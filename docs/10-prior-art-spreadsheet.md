# 10 — Prior art: the spreadsheet

Sources and exported sheets: [`googleSheets/`](googleSheets/).

I initially characterised the spreadsheet as a grid with no constraints, no
coverage view and no per-person output. **That was wrong on all three counts**,
and the correction matters, because a replacement has to be better than what
exists rather than better than a straw man.

## 1. What it actually does

| Capability | How |
| --- | --- |
| **Per-cell eligibility** | `_dropdowns` holds one column of eligible volunteer names per (mission × slot) pair — 18 missions × 29 slots = **522 precomputed columns**. Each cell of the assignment grid gets a data-validation rule pointing at its own column, so the dropdown for "Bar, Saturday 14h–16h" lists only volunteers who are both free then *and* eligible for Bar. |
| **Hard rejection of invalid names** | `.setAllowInvalid(false)` — a typed name outside the list is refused outright |
| **Coverage views** | `récap assignation`, `récap par jour`, `récap bénévoles`, plus `somme` columns giving per-volunteer availability and assignment totals |
| **Per-volunteer schedules** | `VOLUNTEER_SUMMARY` scans the grid for a name and renders a human schedule, **merging contiguous slots of the same mission** — four adjacent bar slots print as one 10h–18h line |
| **Change-aware notification** | SHA-256 of each volunteer's rendered schedule, stored per volunteer. Unchanged digest → email skipped entirely |
| **Two message templates** | First contact versus follow-up, chosen by whether a digest already exists |
| **Email and SMS** | `MailApp` for email; OVH (or Twilio) for SMS, with GSM-7 transliteration to stay inside one paid segment |
| **ICS invites and PDF** | Per-shift ICS blobs; the planning sheet exported as a landscape TABLOID PDF |
| **Send safety** | `LockService` against double-sends, a dry-run mode, a test mode routing everything to one address, per-volunteer opt-out flags, and a check refusing to send unless running as the association's account |
| **Roster versioning** | A `version du planning` cell |

That is a substantial system. Several of its mechanisms are *better thought
out* than what I had specified.

## 2. The actual flaw

The user's own diagnosis, and it is exact:

> the data validation dropdown approach doesn't allow to remove the already
> selected volunteer from the data validation as it would invalidate it

This deserves stating precisely, because it is the entire justification for the
replacement.

To prevent double-booking with data validation, an assigned volunteer would
have to disappear from every *other* dropdown covering the same time slot. But
a Google Sheets validation rule is a **static range reference**, and a cell
whose value is not in its range is flagged invalid. So removing "Camille" from
the 14h–16h lists would invalidate the very cell that just assigned her.

The two requirements are mutually exclusive:

- *Show only assignable volunteers* → the assigned one must leave the list.
- *Keep existing assignments valid* → the assigned one must stay in the list.

There is no configuration that satisfies both. **Double-booking is unpreventable
by construction**, not through oversight. The system can validate that a name is
*eligible*; it cannot validate that the name is *still free*, because that
depends on the current contents of other cells, and validation ranges cannot
see them.

This is precisely the class of invariant that
`EXCLUDE USING gist (volunteer_id WITH =, period WITH &&)` enforces
([03 §3.6](03-data-model.md#36-assignments--where-the-invariants-live)). Not
"the spreadsheet has no constraints" — it has good constraints, and the one
constraint that matters most is the one its constraint mechanism cannot
express.

## 3. The other real limits

| Limit | Detail |
| --- | --- |
| **Eligibility is a stale cross-product** | `_dropdowns` is regenerated by running a script. Between runs it is stale: change someone's availability and the dropdowns still offer them. It also grows as *missions × slots*, so a bigger event multiplies the precomputation rather than adding to it. |
| **Identity is a lowercased name string** | `cleanNameToLowerCase` — matching is `trim().toLowerCase()` equality on the displayed name. Rename someone in one sheet and their assignments silently orphan: `VOLUNTEER_SUMMARY` returns nothing, and they receive a "we couldn't assign you any slots" email. The exported data contains two live instances of this: one volunteer with a double space in one sheet and a single space in another, and one with a differently-cased surname. |
| **Availability is coarse, and split across five questions** | The form asks availability once per sub-event — montage/démontage, Open Air, soirée 1, soirée 2, Afterclash — because a single checkbox list would be unusable. Answers are labels like `"Samedi 5 sept. - Open Air 10h/14h"`. Nobody can express 14h–19h30. |
| **No audit trail** | Nothing records who assigned whom, or when. Revision history is not usable for this. |
| **Concurrency** | `LockService` protects sends, but nothing protects the grid. Two coordinators editing overwrite each other silently. |
| **Scaling pressure** | Custom functions like `VOLUNTEER_SUMMARY` re-read named ranges on every recalculation, once per volunteer per recap sheet. Combined with the 522-column precomputation and Apps Script's execution-time and mail quotas, growth is superlinear in a way that is hard to see coming. Which specific ceiling was hit first is not recorded, so the replacement targets all of them by not doing this work in a spreadsheet at all. |
| **The slot division is a property of the grid** | The 29 slots are columns, so all 18 missions are cut identically. *Artiste* genuinely runs `45 / 45 / 90 / 45 / 45`, and there is nowhere to say so: it is rounded onto the 2-hour grid, or spread across cells that mean something else. This one is easy to miss as a defect, because the sheet offers no alternative to notice it against. |

## 4. What the design takes from it

Seven mechanisms adopted, and one design reversed.

### Already in the design, independently — now validated

**Digest-based change detection.** `schedule_snapshots.digest`
([03 §3.7](03-data-model.md#37-publication)) is the same idea as the SHA-256
recap column: hash each volunteer's schedule, notify only on change. Arriving
at it twice is good evidence it is right.

### Newly adopted

| From the spreadsheet | Now in the design |
| --- | --- |
| First-contact vs follow-up templates | Publish emails distinguish a first schedule from a change, and the follow-up says *what* changed rather than resending a list |
| **"You no longer have any slots"** | A volunteer who had assignments and now has none gets an explicit message. I had missed this entirely — silence is the worst possible output, and it is the case most likely to cause someone to turn up anyway, or not turn up when they should |
| Per-volunteer notification opt-out | `isEmailDisabled` / `isSmsDisabled` → an opt-out flag on the volunteer, respected by the publish worker |
| Dry run *and* test mode | `publish/preview` gives the dry run; a test mode routing every message to one address is added, because previewing a diff is not the same as seeing the rendered email |
| Contiguous slot merging in output | Schedules render adjacent same-post shifts as one line. Purely presentational, and it is the difference between a readable schedule and a wall of half-hours |
| SMS, with GSM-7 optimisation | Promoted from "later, if email proves inadequate" to a real channel. It is already in use, and the transliteration-to-one-segment detail is a cost concern I would not have anticipated |
| Sender-account lock | An operational guard: the publish worker refuses to send unless configured with the organisation's own sending identity |

SMS moving into scope is the largest correction. I had reasoned that email plus
ICS would be sufficient and that SMS could wait for evidence. The evidence
already existed: it is implemented, and it is the channel that works for
day-of changes when nobody is reading email.

### Reversed: names are not first + last

The exported pool holds 75 names in at least a dozen shapes: `SURNAME
Firstname`, `Firstname surname`, `Firstname SURNAME`, bare mononyms (`Jo`,
`Kev`, `Sami`), stage names (`Gibson`, `Moustache`, `Zoravel`), a name with an
emoji, one with a parenthesised nickname, one with a dot inside it, three- and
four-token names, particles (`Le Goff`, `De sousa`), and hyphenated compounds.

My schema had `first_name` and `last_name` required, and my intake mapping
offered a `split` transform as the way to fill them from a single form field.
Against this data the *split* is unsound — it would mangle a majority of the
pool and invent a surname for people who never gave one.

So `volunteers.display_name` becomes the canonical, required field, stored
verbatim and never parsed.

The parts survive, though, and this is where my first correction over-corrected.
`first_name` and `last_name` remain as **optional columns that the form asks
for directly** — because a greeting needs the first name alone ("Bonjour
Camille", not "Bonjour MARCHAND Aurel"), and a surname is what tells two
Camilles apart in a pool of several hundred. Asking two questions is not
parsing one field, and since we own the form
([ADR-0010](adr/0010-first-party-form-as-primary-intake.md)) we can simply ask.

The legacy import leaves both parts `NULL` and fills `display_name` only.

See [ADR-0012](adr/0012-name-parts-asked-not-parsed.md), which supersedes
[ADR-0011](adr/0011-single-display-name-not-first-last.md).

## 5. What is deliberately *not* taken

**The mission × slot eligibility matrix, as a precomputation.** The idea is
right and the implementation is the only one a spreadsheet allows. In the
replacement the same information is a query, evaluated on demand
([03 §5](03-data-model.md#5-query-notes)), so it cannot go stale and does not
grow as a cross-product.

**Name-keyed everything.** Replaced by surrogate keys, with `display_name` as a
label rather than an identifier. `last_name`, where present, is used as a
corroborating signal during identity reconciliation — never as the key.

**Notification state stored beside the data it describes.** `isEmailSent` and
the digest columns live in the same sheet as the roster, so a copy of the sheet
carries stale send state. In the replacement, publication state is its own
table keyed by roster version.
