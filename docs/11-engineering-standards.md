# 11 — Engineering standards

Security-by-design is [12 — Security](12-security.md). This document is
language strictness, type discipline, testing and review.

## 1. The governing rule

**A standard without a gate is a suggestion.** Every rule below is either
enforced by a compiler flag, a lint, or a test or check run by `just check` /
`just test` — or it is explicitly marked *judgement*, meaning it is a review
conversation and nothing more. A gate that is specified but not yet built is
marked *planned* in §7; there is no hosted CI yet, so the local recipes are
the gate.

Two corollaries that matter more than the rules themselves:

- **Warnings while iterating, errors at the gate.** `cargo build` warns so that
  working is not miserable; `just check` runs clippy with `-D warnings` so
  nothing merges dirty. A lint that
  blocks your own iteration gets disabled; a lint that blocks the merge gets
  fixed.
- **Suppressions must justify themselves.** Use `#[expect(lint, reason = "…")]`
  rather than `#[allow]` — an `expect` that stops being necessary becomes a
  warning, so suppressions cannot silently outlive their reason. In TypeScript,
  `eslint-disable` requires a description
  (`reportUnusedDisableDirectives: "error"` plus
  `@eslint-community/eslint-comments/require-description`).

## 2. Rust

### Workspace lints

Declared once in the root `Cargo.toml` (`[workspace.lints]`, Rust ≥ 1.74) and
inherited by every crate with `[lints] workspace = true`. One place to look,
impossible to forget in a new crate.

```toml
[workspace.lints.rust]
unsafe_code                = "forbid"   # not "deny" — cannot be re-allowed locally
unreachable_pub            = "warn"
unused_qualifications      = "warn"
unused_must_use            = "deny"
missing_debug_implementations = "warn"
rust_2018_idioms           = { level = "warn", priority = -1 }

[workspace.lints.clippy]
all      = { level = "deny",  priority = -1 }
pedantic = { level = "warn",  priority = -1 }

# Panicking constructs. A server must not have them in library code.
unwrap_used              = "deny"
expect_used              = "deny"
panic                    = "deny"
indexing_slicing         = "deny"
unreachable              = "deny"
todo                     = "deny"
unimplemented            = "deny"

# Silent-wrong-answer constructs
arithmetic_side_effects  = "deny"   # forces checked_/saturating_ on time maths
as_conversions           = "deny"   # forces TryFrom, so truncation is handled
float_arithmetic         = "deny"   # hours are Decimal, never f64
cast_possible_truncation = "deny"
lossy_float_literal      = "deny"

# Hygiene
dbg_macro                = "deny"
print_stdout             = "deny"   # use tracing
print_stderr             = "deny"
mem_forget               = "deny"
```

Tests and binaries relax the panicking group — `#![cfg_attr(test, allow(clippy::unwrap_used))]`
in test modules, and `main.rs` may `expect` on startup configuration, because
failing to boot loudly is correct.

`unsafe_code = "forbid"` rather than `"deny"`: `forbid` cannot be overridden by
an inner `allow`. Nothing in a volunteer planner needs `unsafe`, and the day
someone thinks it does is the day it should require changing this file, visibly,
in review.

`arithmetic_side_effects` and `as_conversions` are the two that will feel
onerous. They are deliberate: this application does arithmetic on **times and
headcounts**, where a silent wraparound or a truncating cast produces a
schedule that is wrong rather than a program that crashes. Wrong schedules are
the failure mode this project exists to prevent.

### Profiles

```toml
[profile.release]
overflow-checks = true    # NOT the default in release
debug           = 1       # line tables, so production panics have locations
lto             = "thin"
```

`overflow-checks` in release is the important line. By default, release builds
wrap silently on overflow while debug builds panic — meaning integer bugs are
found only in development, which is exactly backwards.

### Types

**Newtype every identifier.** The schema has a dozen UUID-keyed entities, and
`Uuid` accepts any of them.

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, Serialize, Deserialize, sqlx::Type)]
#[sqlx(transparent)]
pub struct VolunteerId(Uuid);
```

Generated by a macro, one line each. It makes
`assign(shift_id, volunteer_id)` called with the arguments swapped a **compile
error** rather than a data corruption. Cheap, and it retires an entire bug
class.

**Never `String` for a constrained value.** `Email`, `Phone`, `Slug`,
`TimeZone`, `RuleCode` are types with fallible constructors. Parse once at the
boundary; downstream code cannot receive an invalid one.

**Times are typed and injected.** `jiff::Timestamp` and `jiff::Zoned`, never
`String`, never a naive local type, and never the `time` crate's
`OffsetDateTime` — the choice is `jiff`, for the reasons in
[ADR-0019](adr/0019-time-discipline.md), and one date library is enough. `now()`
comes from a `Clock` trait so tests control it — a test that depends on
wall-clock time is a flaky test waiting for a DST boundary.

**Durations and hours are `Decimal`**, matching `numeric(4,2)` in the schema.
`f64` for hours-per-day gives you `9.999999999999998 > 10`.

**Errors:** `thiserror` in libraries with meaningful variants; `anyhow` only in
`main` and the CLI. Exactly one place converts a domain error into an HTTP
response, so a new variant cannot accidentally leak its `Display` text to a
client ([12 §5](12-security.md#5-not-leaking-things)).

**Make illegal states unrepresentable** where the type system can. An
`Assignment` in the domain carries its acknowledged warnings, so there is no
way to construct one that bypassed the engine.

### Async and panics

- No blocking I/O on the async runtime. CPU-bound work (PDF rendering) goes
  through `spawn_blocking`.
- `tower_http::catch_panic::CatchPanicLayer` turns a panicked handler into a
  `500` instead of killing the process and every in-flight request with it.
- A panic in production is a **P1 bug**, not a handled condition: it increments
  a counter that is alerted on. The lints above exist so that reaching one
  requires a genuine mistake.

### Toolchain

`rust-toolchain.toml` pins the exact version so every developer and every build
compiles identically. `rust-version` in `Cargo.toml` declares the MSRV. Bumping
either is a deliberate commit.

## 3. TypeScript

### `strict: true` is necessary and not sufficient

`strict` leaves the two highest-value checks off. Both are on here.

```jsonc
{
  "compilerOptions": {
    "strict": true,

    // The two that strict does not include
    "noUncheckedIndexedAccess": true,      // arr[i] is T | undefined
    "exactOptionalPropertyTypes": true,    // {a?: string} ≠ {a: string | undefined}

    "noImplicitOverride": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,
    "noPropertyAccessFromIndexSignature": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "allowUnreachableCode": false,
    "allowUnusedLabels": false,

    "verbatimModuleSyntax": true,
    "isolatedModules": true,
    "erasableSyntaxOnly": true,            // no enums, namespaces, param properties
    "noEmit": true,                        // Vite builds; tsc only type-checks
    "skipLibCheck": false
  }
}
```

`noUncheckedIndexedAccess` is the one worth defending. The planner board indexes
into arrays of shifts and time buckets constantly; without it, `shifts[i].period`
type-checks and throws at runtime on an off-by-one. With it, the compiler makes
you handle the empty case. It is mildly annoying in loops and worth it.

`skipLibCheck: false` is contrary to common advice. Dependency types are part of
the build's correctness, and the dependency tree here is small enough to check.

Type-checking `.vue` files is `vue-tsc --noEmit`, in `just check` (`pnpm typecheck`).

### Banned constructs

| Banned | Rule | Why |
| --- | --- | --- |
| `any` | `@typescript-eslint/no-explicit-any: error`, plus the `no-unsafe-*` family from `strictTypeChecked` | An `any` disables checking transitively, silently |
| `!` non-null assertion | `@typescript-eslint/no-non-null-assertion: error` | The TypeScript equivalent of `unwrap()` |
| `as` type assertions | `consistent-type-assertions: { assertionStyle: "never" }` | Assertions *assert*; they do not check. Use a type guard or parse the value |
| `enum` | `no-restricted-syntax` | Not erasable, has surprising runtime semantics. Use `as const` unions |
| `v-html` | `vue/no-v-html: error` | The XSS vector in a Vue app ([12 §4](12-security.md#the-frontend)) |
| Hand-written API types | Regeneration diff (planned) | The client is to be generated from OpenAPI ([ADR-0030](adr/0030-backend-dependency-selection.md)); drift is then a build failure. **Not built yet:** today each module in `apps/admin/src/api/` declares valibot schemas by hand and parses every response with them |
| `console.log` | `no-console: error` | Ships to production and can leak PII |

ESLint runs on `@typescript-eslint` **`strictTypeChecked`** plus
`stylisticTypeChecked` — the type-aware configs, not the syntactic ones. The
`no-unsafe-argument` / `no-unsafe-member-access` rules in that set are what
actually catch `any` leaking in from an untyped dependency, and they require
type information to work.

### Types are not validation

The generated client, once it exists, gives compile-time types for *our* API.
It gives no runtime guarantee, and several inputs are outside it entirely.
Until then the admin's hand-written valibot schemas are both the types and the
runtime check.

**Parse, don't cast, at every boundary:** URL and query parameters,
`localStorage`, form input before submit, and anything from `postMessage`. Use
**valibot** rather than zod in the public form bundle — same parse-don't-validate
model, materially smaller, and that bundle is loaded once on a phone
([09 §6](09-volunteer-form.md#6-rendering-it)). The admin bundle may use either.

A parsed value gets a branded type, so unparsed input cannot reach code that
expects a validated one.

## 4. SQL and migrations

- Queries are meant to go through SQLx macros (`query!`, `query_as!`), which
  are checked against the real schema at compile time, with
  `cargo sqlx prepare --check` in `just check` so a query cannot drift from the
  schema. **Not yet:** every query today is a runtime `sqlx::query*` call and
  there is no committed `.sqlx/` cache, so the check passes vacuously and SQL
  is verified by the integration suite alone. `crates/evp-db/src/auth.rs` and
  `lib.rs` record why the first modules were written that way.
- **No dynamically constructed SQL.** Filters use `QueryBuilder` with bound
  parameters. A grep rejecting `format!`/`push_str` producing SQL is planned;
  until it exists this is a review item — see
  [12 §3](12-security.md#3-the-database-boundary).
- Migrations are **forward-only, immutable once applied, and never edited**. A
  mistake is corrected by a new migration.
- A migration that drops a column or table, or that could lose data, needs an
  explicit reviewer sign-off noted in the pull request. Additive-only is the default.
- Every migration is tested by running the suite against a database built from
  migrations alone — never from a hand-maintained schema dump.

## 5. Testing

Discipline, TDD scope and the efficacy gates are
[13 — Testing and TDD](13-testing-and-tdd.md); tooling and what runs where is
[06 §4](06-local-development.md#4-testing-strategy). The standards that bear on
code shape:

- **Every hard constraint has a test that attempts the violation** and asserts
  the specific SQLSTATE. A constraint nobody tried to break is a constraint you
  are guessing about.
- **Every rule in the constraint engine gets three tests**: passing, failing,
  and the boundary. A shift ending exactly when another begins is *not* an
  overlap, and that assertion is what stops a later "simplification" flipping
  `>=` to `>`.
- **No test reads the wall clock.** Inject `Clock`.
- **Never mock the database** — the invariants live in PostgreSQL, so a mocked
  repository tests a fiction ([13 §6](13-testing-and-tdd.md#6-do-not-mock-the-database)).
- **Tests are named for the behaviour**, not the function:
  `refuses_overlapping_assignment_for_same_volunteer`.

## 6. Style and structure

*Judgement, not gated* — these are review conversations.

- `rustfmt` and `prettier` with default settings, no bikeshedding, applied by
  the pre-commit hook.
- Functions do one thing; if a name needs "and", split it.
- Comments explain **why**, never what. The code says what. A comment restating
  the code is deleted on sight; a comment recording *why the obvious approach is
  wrong here* is the most valuable line in the file.
- No dead code, no commented-out code, no "keep for later". Git remembers.
- Dependency direction is inward: `api`/`worker` → `domain`/`db`, and `domain`
  depends on neither ([02 §3](02-architecture.md#3-backend-structure)). A new
  dependency that points outward is rejected.
- Frontend: no business logic in components. Rules live in composables and are
  unit-tested without mounting anything.

## 7. Enforcement summary

Status: **enforced** runs today in `just check` or `just test`; **partial**
exists but covers less than the rule; **planned** is specified and not built.
There is no hosted CI yet ([06 §5](06-local-development.md#5-ci)).

| Standard | Gate | Stage | Status |
| --- | --- | --- | --- |
| Formatting | `cargo fmt --check`, `prettier --check` (`just check`) | check | enforced |
| Rust lints | `cargo clippy -- -D warnings` (`just check`) | check | enforced |
| No `unsafe` | `forbid(unsafe_code)` | compile | enforced |
| Overflow checks in release | `Cargo.toml` profile | compile | enforced |
| TS strictness | `tsc --noEmit`, `vue-tsc --noEmit` (`pnpm typecheck`) | check | enforced |
| TS banned constructs | `eslint` with `strictTypeChecked` (`pnpm lint`) | check | enforced |
| Unused suppressions | `reportUnusedDisableDirectives`, `#[expect]` | check | enforced |
| SQL matches schema | `cargo sqlx prepare --check` | check | partial — runs, but no query uses the macros yet (§4) |
| No dynamic SQL | grep for SQL built by string formatting | check | planned |
| API client not hand-edited | regeneration diff | check | planned — no generated client yet (§3) |
| OpenAPI contract stable | snapshot test | test | planned |
| Hard constraints hold | integration suite (`just test`) | test | enforced |
