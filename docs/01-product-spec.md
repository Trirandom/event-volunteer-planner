# 01 — Product specification

## 1. Why this exists

Volunteer planning is currently done in Google Sheets, with a substantial Apps
Script layer around it. Analysis of that system is
[10 — Prior art](10-prior-art-spreadsheet.md); the sources are in
[`googleSheets/`](googleSheets/).

It is important to be accurate about what the spreadsheet does, because the
replacement has to beat the real thing. It already has:

- **per-cell eligibility** — each cell of the assignment grid carries a
  data-validation list of exactly the volunteers who are free at that time
  *and* eligible for that mission, precomputed across missions × slots;
- **coverage views** — per-day, per-volunteer and per-assignment pivots, with
  availability and workload totals;
- **per-volunteer schedule emails and SMS**, with a SHA-256 digest per person
  so unchanged schedules are not resent, separate first-contact and follow-up
  templates, dry-run and test modes, and per-volunteer opt-outs;
- ICS invites, and a PDF export of the whole planning.

So the problem is not absence of features. It is one specific, unfixable
defect, plus the cost of maintaining the rest in a spreadsheet.

### The defect

**Data validation cannot prevent double-booking.** To stop it, an assigned
volunteer would have to vanish from every other dropdown covering the same
time. But a validation rule is a static range, and a cell whose value is not in
its range is marked invalid — so removing someone from the 14h–16h lists
invalidates the very cell that just assigned them.

*Show only assignable people* and *keep existing assignments valid* cannot both
hold. Double-booking is therefore unpreventable by construction. The system can
check that a name is **eligible**; it cannot check that the name is still
**free**, because that depends on the contents of other cells, which a
validation range cannot see.

That is the whole argument for this project, and it is why the replacement
enforces overlap in the database rather than in the interface
([05](05-scheduling-rules.md)).

### The rest

| | |
| --- | --- |
| **Eligibility goes stale** | The per-cell lists are regenerated by running a script. Change an availability and the dropdowns still offer the old answer. The precomputation also grows as missions × slots. |
| **Identity is a lowercased name** | Matching is `trim().toLowerCase()` on the displayed name. Rename someone in one sheet and their assignments silently orphan — they then receive a "we couldn't assign you any slots" email. The live data contains two instances of this. |
| **Availability is coarse** | The form asks it once per sub-event, as checkbox labels like `"Samedi 5 sept. - Open Air 10h/14h"`, because no general-purpose form can ask for a time range. Nobody can say 14h–19h30. |
| **One slot grid for every mission** | The 29 columns are a property of the sheet, so all 18 missions are cut the same way. *Artiste* actually runs `45 / 45 / 90 / 45 / 45`; in the grid it has to be rounded or misrepresented. |
| **No audit trail** | Nothing records who assigned whom, or when. |
| **No safe concurrency** | Sends are lock-protected; the grid is not. Two coordinators overwrite each other silently. |
| **Superlinear cost** | Custom functions re-read named ranges per volunteer per recap sheet, on every recalculation, alongside the cross-product precomputation and Apps Script's execution and mail quotas. |

The goal is therefore **not** "a spreadsheet with more rows", and not "a
spreadsheet with features it lacks". It is: *keep everything that system got
right, and make the one invariant it cannot express impossible to violate.*

## 2. Scope

### In scope for v1

- Multi-tenant: several independent organisations on one deployment, fully
  isolated from each other.
- Self-hostable and provider-agnostic: this is open source (AGPL-3.0-or-later),
  so no deployment is required to use any particular identity provider, mail
  service or form tool.
- **Source availability to network users**, as AGPL §13 requires: every person
  who interacts with a deployment — coordinators and volunteers alike — can
  reach the source of the version they are using.
- Multiple events per organisation, and multiple editions of a recurring event.
- A reusable volunteer pool per organisation, carried across events.
- Skills/qualifications with expiry dates.
- Volunteer-declared availability windows, collected by form.
- A location hierarchy (zone → post) per event.
- Shifts with a required headcount and skill requirements.
- **Per-mission slot divisions**: 2 hours by default, and any other division a
  mission needs — the *artiste* post runs `45 / 45 / 90 / 45 / 45`. Reusable
  across events, and generating rather than binding
  ([ADR-0029](adr/0029-shift-patterns-are-generators-not-constraints.md)).
- **Coordinator-driven assignment.** Volunteers never claim shifts themselves.
- A constraint engine that hard-blocks impossible assignments and warns on
  questionable ones.
- Per-event logistics attributes: meals, T-shirt size, dietary needs,
  accreditation.
- Draft → publish lifecycle, with schedule emails **and SMS** on publish and on
  change — SMS is already in use in the current system, so it is in scope, not
  deferred.
- **Our own volunteer form**, with a real availability picker: per-day, exact
  time ranges, not coarse checkboxes. Reached by a personal link that can be
  reopened to revise an answer, or by a public link for new volunteers.
- An **intake pipeline** behind it — immutable raw answers, identity
  reconciliation, a review queue, and replay — which also handles the one-time
  CSV migration of the existing spreadsheet.
- Audit log of every mutation.

### Explicitly out of scope for v1

| Not doing | Why |
| --- | --- |
| Volunteer accounts or logins | Data comes in by form; schedules go out by email and ICS. Volunteers still read, correct and erase their own record — by capability link, not by login ([ADR-0008](adr/0008-no-volunteer-authentication-in-v1.md), [ADR-0027](adr/0027-volunteer-self-service-rights.md)). |
| Volunteer self-signup for shifts | Assignment model is coordinator-only by decision. Would require accounts. Revisit in v2. |
| Form branching, page logic, file upload | Ten question types, one page, no conditions. [09 §1](09-volunteer-form.md#1-scope). |
| Third-party form integrations (Typeform, Sheets polling) | Specified but not scheduled — our own form is better at the thing that matters. [ADR-0010](adr/0010-first-party-form-as-primary-intake.md). |
| Shift swapping between volunteers | Depends on volunteer identity. A genuine v2 feature, not an extension. |
| Real-time collaborative editing (multiple cursors) | Optimistic concurrency + audit log covers the actual pain. |
| Native mobile apps | Responsive web + ICS feed covers on-site use. |
| Payroll, expense claims, contracts | Different problem domain. |
| Public recruitment / landing pages | Volunteers are already known to the organisation. |
| Push notifications | Email and SMS cover it. |
| Non-OIDC login (GitHub, Discord, LDAP, SAML) directly | Put Dex or Keycloak in front and configure it as one OIDC provider. Per-provider adapters in the core are the maintenance burden [ADR-0014](adr/0014-pluggable-oidc-providers.md) avoids. |
| Per-organisation identity providers | Providers are deployment-wide in v1. Per-org SSO brokering needs providers in the database; noted as the natural extension. |
| Time clock / on-site check-in | Deliberately deferred; see [roadmap](07-roadmap.md). |

## 3. Personas

| Persona | Logs in | Can do |
| --- | --- | --- |
| **Owner** | Yes — SSO or magic link | Everything in their organisation, plus billing-level settings, member invites, and deleting events. |
| **Coordinator** | Yes — SSO or magic link | Build events, shifts and locations; assign volunteers; publish rosters; manage the volunteer pool. |
| **Zone lead** | Yes — SSO or magic link | Read the whole event, assign only within the zones delegated to them. |
| **Volunteer** | **No** | Has no account. Fills in the organisation's form — reached by a personal link, revisable at any time — and receives their schedule by email and as a calendar feed. |

**Volunteers have no accounts at all.** A volunteer is a person record in an
organisation's pool — no login, no session, no authenticated surface. They tell
the organisation things through a form, and the organisation tells them things
by email. See [ADR-0008](adr/0008-no-volunteer-authentication-in-v1.md).

This is a deliberate narrowing. It means the authenticated surface is a few
dozen staff rather than several hundred occasional users, there is no volunteer
account lifecycle to support, and the pool works for people who have no email
address. The cost is that volunteers cannot correct their own records; that is
a message to a coordinator, or a resubmission of the form.

## 4. Core user stories

Acceptance criteria are written so that they are testable.

### Setting up

**S0 — As a coordinator, I sign in with the account my organisation already uses.**
- For this deployment that is Google, one click, no password. Another
  deployment configures Microsoft, Okta, Keycloak or nothing at all — the login
  page renders whatever is configured.
- An emailed link always works too, so the system is never unreachable because
  one provider is down or misconfigured.
- Signing in with a trusted provider for the first time attaches it to my
  existing account when the address matches and the provider says it is
  verified. With an untrusted provider I have to link it deliberately while
  already signed in.
- I can see my active sessions and sign out a device I no longer have.

**S0a — As anyone using a deployment, I can find its source.**
- The admin application shows the version and a source link in its About panel;
  the public volunteer form shows one in its footer.
- `GET /api/v1/meta` returns version, commit and source URL without
  authentication.
- The link points wherever the operator configured, so a modified deployment
  can point at its own fork — which is what makes AGPL §13 compliance a
  configuration value rather than a legal chore.

**S0b — As someone self-hosting this, I can get started with nothing.**
- `docker compose up`, create the first owner from the CLI, sign in by emailed
  link. No Google Cloud Console, no OAuth client, no identity provider.
- Adding SSO later is a config file and a restart, with no code change and no
  frontend rebuild.

**S1 — As an owner, I create an organisation and invite coordinators.**
- Invite is an email link, valid 7 days, single use.
- An accepted invite creates a membership with the role stated in the invite.
- Data written in one organisation is never readable from another, and this is
  enforced at the database level, not only in application code.

**S2 — As a coordinator, I create an event with a timezone.**
- Event has a name, a timezone (IANA), and a start/end datetime.
- All times are stored as `timestamptz` and displayed in the *event's*
  timezone, not the viewer's browser timezone. A festival that runs across a
  DST change must not shift its shifts.

**S3 — As a coordinator, I duplicate last year's event.**
- Copies locations, shifts (rebased onto new dates), and skill requirements.
- Does **not** copy assignments or participations.

### The pool

**S4 — As a coordinator, I build the form volunteers will fill in.**
- I pick from a fixed set of question types and set what each one feeds:
  a volunteer field, a skill, or availability.
- I preview it, then publish. Publishing freezes that version.
- I can edit a live form: that creates a new version, and answers already given
  stay attached to the version that produced them. Nothing I do retroactively
  changes what an earlier answer meant.
- Publishing is refused if the form has no **processing** consent question, or
  that question is not required, or a question has no destination. A **pool
  retention** consent is optional and cannot be marked required
  ([ADR-0025](adr/0025-two-consents-processing-and-pool-retention.md)).
- More than one availability picker, or two consents of the same purpose, cannot
  be saved at all — the database refuses them, in a draft as much as in a
  published version.

**S4b — As a coordinator, I send volunteers their personal link.**
- I issue links to everyone in the pool, or to a filtered subset, in one action.
- Links are emailed, never shown to me — if someone loses theirs, I resend.
- A volunteer reopening their link sees what they told us last time, prefilled.
- I can revoke one link, or rotate all of them.
- I can close the public link while personal links keep working.

**S4c — As a coordinator, I migrate my existing spreadsheet.**
- One-time CSV upload: map columns to fields, preview against real rows, commit.
- Rows that fail are reported with a line number and reason; valid rows in the
  same file still import.
- Re-uploading the same file changes nothing.
- If I got the mapping wrong, I fix it and replay — no re-export.

**S4d — As a coordinator, I resolve who a response belongs to.**
- Responses from a personal link need no resolution — identity is certain.
- Responses from the public link are matched on email, or land in a review queue
  showing the answers beside the candidate volunteers.
- The system never merges two people on a name match alone.
- My manual corrections to a volunteer's record are never overwritten by a
  later submission.

**S5 — As a coordinator, I record skills with expiry.**
- A skill can be marked expired-as-of a date (first-aid certificates lapse).
- An expired skill does not satisfy a shift requirement on a shift that starts
  after the expiry date.

**S6 — As a volunteer, I say exactly when I am available.**
- For each day of the event I give one or more time ranges — 14:00 to 19:30,
  not "afternoon".
- I can tap a suggested window ("Saturday afternoon") and then adjust it, drag
  on the day's track, or type the times. All three work; typing works on a
  phone and with a screen reader.
- I can say "not available at all" for a day, which is different from saying
  nothing.
- Times are shown in the event's timezone, labelled as such.
- If I submit again, my new answer replaces the old one entirely — withdrawing
  availability works.
- A coordinator can also enter this for me over the phone, and the record shows
  which of us it came from.

**S6b — As a volunteer, I change my mind later.**
- My personal link still works. I reopen it, see what I said, change it, and
  resubmit.
- No password, no account, no app.

**S6c — As a volunteer, I can see, correct and delete what is held about me.**
- The same personal link shows me what the organisation holds, and lets me
  correct my own details — even months later, when no form is live.
- I can turn off email or SMS, or withdraw permission to keep my details for
  next year, in one click and with no confirmation step.
- I can ask for everything held about me, and it is emailed to me.
- I can ask for it to be deleted. Because my link is forwardable, deletion is
  confirmed by an email to the address on record before anything is destroyed.
- None of this needs an account ([ADR-0027](adr/0027-volunteer-self-service-rights.md)).

### Planning

**S7 — As a coordinator, I lay out locations and shifts.**
- Locations nest one level: zone → post.
- A shift belongs to one location, has a time range and a required headcount.
- Shifts can be created in bulk ("every day 08:00–12:00 from the 4th to the
  7th, at these 5 posts").

**S7b — As a coordinator, I decide how each mission is cut into slots.**
- Two hours is the default, because that is what most missions run on. I change
  it once for the event rather than per shift.
- A mission whose day is not shaped like that gets its own division. *Artiste*
  is two 45-minute slots, then 90 minutes, then two more of 45 — I describe that
  once, name it, and attach it to the post.
- A division can include dead time — a changeover, a sound check, a meal — which
  consumes the window and produces no shift.
- I name a division and reuse it next year and at the next event. Duplicating an
  event keeps it.
- I preview what will be generated before anything is written, and one
  `Ctrl+Z` removes the whole run.
- **Generated shifts are ordinary shifts.** I can drag one to end at 10:20
  because that is when the artist actually finishes, and nothing objects, warns,
  or offers to put it back ([ADR-0029](adr/0029-shift-patterns-are-generators-not-constraints.md)).
- The system refuses to attach a division finer than what the volunteer form can
  express — 45-minute slots against a 30-minute availability picker — and tells
  me to lower the picker's step rather than accepting a mismatch it would then
  warn about on every assignment.

**S8 — As a coordinator, I assign volunteers to shifts.**
- The UI is a timeline: locations on the vertical axis, time on the horizontal,
  shifts as blocks, and a filterable volunteer panel beside it.
- When two candidates share a first name, the panel shows their surnames so I
  can tell which is which. I am never asked to pick between two identical
  labels.
- Assigning is drag-and-drop and also fully keyboard-operable.
- The system **refuses** an assignment that double-books a volunteer.
- The system **warns**, but allows with an explicit acknowledgement, on: skill
  mismatch, outside declared availability, over headcount, too little rest
  between shifts, or over the daily hour cap.
- Every override records who acknowledged it and when.

**S8b — As a coordinator, I make large changes quickly, and I can undo them.**
- I select several volunteers and several shifts and assign them in one action.
  The ones that clash are reported by name and reason; the rest are applied. The
  whole action is not thrown away because one person is busy.
- I can copy a day's roster onto another day, replace one volunteer with another
  across a selection, and clear a selection.
- `Ctrl+Z` undoes any of it, including after a page reload, because the undo is
  recorded on the server ([ADR-0024](adr/0024-server-side-undo-and-per-item-bulk.md)).
- Undo is refused once a roster has been published — that already sent email, so
  the correction is a new change and a republish — and the refusal says so.

**S9 — As a coordinator, I see what is not yet covered.**
- A coverage view lists every shift that is under its required headcount, or
  missing a required skill, grouped by day and zone.
- The number of gaps is visible at all times, not behind a report button.

### Publishing and output

**S9b — As a coordinator, messages address volunteers by their first name.**
- Emails and SMS greet people as "Camille", not "MARCHAND Aurel".
- Volunteers who only ever gave one name are greeted by that name.
- Printed rosters still show the full name they gave, because that is what
  people are recognised by on site.

**S10 — As a coordinator, I publish the roster.**
- Publishing snapshots the current assignments as a new roster version.
- Each affected volunteer receives their personal schedule by email, and by SMS
  where they have a number and have not opted out.
- Republishing after a change notifies **only** the volunteers whose schedule
  actually changed, and says what changed.
- A volunteer who previously had shifts and now has none receives an explicit
  message saying so. Silence is not an acceptable output for that case.
- Adjacent shifts at the same post render as one line — "Sam. 5/9 10h–18h :
  Bar", not four half-day entries.
- I can preview the diff, and separately send the whole run to a single test
  address to see the rendered messages before anyone else does.
- Volunteers I have marked as not-to-be-contacted are skipped, and the run
  reports that it skipped them.

**S11 — As a coordinator, I produce the on-site paperwork.**
- Per-post roster sheets, per-volunteer schedule cards, an accreditation list,
  and meal counts per service — all exportable as PDF and CSV.

**S12 — As a volunteer, I get my schedule on my phone.**
- A personal ICS subscription URL, containing only my own shifts at this event,
  delivered in my schedule email. My calendar app polls it; no login and no app.
- It stops working once the event is over and its data has been cleared, which
  is also when it stops being useful.
- The URL carries an unguessable token, is revocable, and grants read access to
  that one calendar and nothing else.

### Accountability

**S13 — As an owner, I can see who changed what.**
- Every create/update/delete on events, shifts, assignments and volunteers is
  recorded with actor, timestamp, and before/after values.
- Two coordinators editing the same shift do not silently overwrite each other:
  the second write is rejected with a conflict the UI can resolve.

## 5. Non-functional requirements

Target scale is **500 volunteers, ~5000 shift-assignments per event, a handful
of events per year, and at most ~20 concurrent coordinator sessions.**

That is small. It is worth stating plainly, because it means the correct
architecture is a single API process and a single database, and any design that
introduces caching layers, sharding or a message broker for *performance*
reasons is over-engineering. The stack choices below are made for correctness,
operability and low idle cost — not throughput.

| Requirement | Target |
| --- | --- |
| Volunteer form first paint | < 1.5 s on a cold load, 3G-fast, at 400 px. It must *work* down to 320 px, which is the conformance floor ([14 §2](14-accessibility-and-interaction.md#2-ground-rules)); 400 px is the width it is designed for |
| Timeline view first paint | < 1.5 s on a cold load, 3G-fast |
| Assignment write, server-side | p99 < 100 ms |
| Coverage recomputation for a full event | < 500 ms server-side |
| Idle memory, whole stack | < 512 MB |
| SMS cost | Messages are transliterated to GSM-7 so a schedule fits one paid segment wherever possible |
| Backup | Nightly `pg_dump`, plus WAL archiving; restore drill documented |
| Data retention | Events archivable; personal data deletable per volunteer (GDPR) |
| Licence compliance | Source link and version visible to every network user, on both frontends; dependency licences checked against an allow-list |
| Code strictness | No `unsafe`; panicking and truncating constructs denied; TypeScript `strict` plus `noUncheckedIndexedAccess`. All gated by `just check` ([11](11-engineering-standards.md)) |
| Security invariants | Tenant isolation, double-booking and authorisation enforced structurally — by RLS, constraints and typed extractors — not by review ([12](12-security.md)) |
| Accessibility | WCAG 2.2 AA. Every drag has a keyboard equivalent; a keyboard-only journey is a test gate ([14](14-accessibility-and-interaction.md)) |
| Time correctness | Storage independent of the server timezone, proven by re-running the suite under a hostile `TZ` ([16](16-i18n-and-time.md)) |
| Availability | Best-effort. Scheduled downtime is acceptable outside event weeks. |

## 6. Privacy

Volunteer records are personal data: names, emails, phone numbers, dietary
requirements (which can imply religion or health). This carries obligations.

- Dietary and medical notes are treated as sensitive: not included in exports
  by default, and visible only to coordinators, not zone leads.
- Every volunteer record supports export and hard deletion on request.
- Audit log entries are pseudonymised rather than deleted when a volunteer is
  erased, so history stays consistent.
- **Retention is by purpose** ([15](15-privacy-and-retention.md),
  [ADR-0018](adr/0018-purpose-based-retention.md)): event-scoped personal data
  is deleted automatically 30 days after the event; the volunteer's own stable
  record is kept only with separate, explicit consent, expiring 18 months after
  last contact. Which tier something is in follows **which table it is on**, and
  every table declares its tier in the schema, so the rule cannot drift from the
  data model ([ADR-0021](adr/0021-retention-tier-follows-table.md),
  [ADR-0026](adr/0026-retention-scope-is-a-table-registry.md)). The periods are
  per-organisation configuration with caps the schema enforces
  ([ADR-0020](adr/0020-retention-periods-are-configuration.md)).
  The earlier "flag for review after 24 months" rule was replaced — a review
  flag is not a lawful basis for keeping personal data.
- **GDPR sets no numeric retention maximum**; the periods above are this
  software's defaults, justified in [15 §2](15-privacy-and-retention.md#2-what-the-law-actually-says),
  not legal requirements.
- Volunteers can see, correct, export and erase their data **at any time**,
  self-service from their form link and without an account
  ([ADR-0027](adr/0027-volunteer-self-service-rights.md)). Erasure is confirmed
  to the address on record, so a forwarded link cannot delete someone else's
  data. The link lasts as long as the record it reaches, which is what makes
  "at any time" true rather than "during the campaign".
- **Raw form submissions are personal data**, and are the largest concentration
  of it: a verbatim copy of everything a volunteer typed. They are stored apart
  from the submission record and **deleted 30 days after they arrive**, whether
  or not any event has ended; erasing a volunteer deletes theirs at once.
